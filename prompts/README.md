# 提示词使用说明

这些模板与[设计说明](../docs/design.md)配合使用。它们描述模型行为；持久化、权限、筛选、预算和实际历史裁剪需要程序实现。本包没有注册任何检索工具，也没有修改 Coopanion 的配置。

| [对话策略（中文）](companion-policy.zh.md) / [English](companion-policy.en.md) | 现有角色提示词末尾，二选一 | 依据有限快照对话，不虚构已恢复的记忆 |
| [增量记忆提取](memory-extractor.zh.md) | 独立维护流程 | 只从新增用户信息提出带来源的变更 |
| [可选线索判定](cue-router.zh.md) | 规则无法明确判断时 | 判断是否存在用户提供的回忆线索 |
| [跨天性格与近期状态](persona-continuity.zh.md) / [English](persona-continuity.en.md) | 启用连续性配置时，分别用于主对话与独立维护 | 持久接续当前风格、近期状态和细节，按规则渐变 |
| [主动陪伴](proactive-companion.zh.md) / [English](proactive-companion.en.md) | 用户明确开启，宿主已实现范围授权时，补充主对话 | 结合情绪和当前话题有限回忆，再决定是否提起 |

## 接入约定

- 提示词文件内标出的“可复制提示词”才是模型指令。外围说明不必每次发送。
- 主对话模型只接收 `memory_snapshot`，其中 `pinned`、`hot`、`recalled` 都已由程序筛选和限额。正文项至少有 `id`、`summary`、`source_refs`、`created_at`，如有事件时间另给 `occurred_time`；created_at 只表示入库，不能当作事件发生时间。候选卡可仅给ID、短标题和用于区分的已知时间/类型，仍与正文共用召回额度；封装字段也计入预算。
- 可选连续性配置在 hot 中放一个 `kind=continuity_state` 的紧凑记录，完整维护状态留在宿主；hot 内按 320 / 320 / 320 分给状态、近期细节和话题事实。风格可跨话题延续，事件不可借此绕过相关性、“问到再说”或冷检索限制。详见[连续性设计](../docs/persona-continuity.md)。
- 另有可信元数据 `recall_status`、`cue_scope`、`budget_mode`，由宿主生成。状态为 `disabled / matched / ambiguous / not_found`。可信状态与来自记忆的文本在协议中分隔，不能允许原文覆盖状态。
- 若宿主尚未支持快照，主提示词只能改善回答习惯，不能提供硬性冷存或预算保证。不得让模型凭空调用这里没有注册的工具。
- 抽取器与线索判定器输出都是建议。宿主独立保存每轮用户与助手的对话原文；抽取器只决定哪些内容值得另做短记忆卡，不能因没有卡片就丢掉该轮原文。程序校验事件身份、来源、ID、长度、权限和版本后再执行。校验失败不扩大检索权限；用户明确删除的原文和派生副本须清除。
- 不要把本仓库全部文档塞进系统提示词。一次主对话只使用对话策略与有限快照，其他模板按需独立运行。

## 向量排序由程序执行

可选的[向量配置](../config/vector-ranking.example.json)负责事件向量、当前问题相似度、热区时间衰减与有限 Top N；[设计](../docs/vector-ranking.md)规定冷召回不惩罚年代。向量、全库分数、索引和本文档不随每轮提示词发送。主对话仍只接收原有额度内的文字快照；连续性状态保留独立空间。抽取器只提出有来源的事件内容，不生成伪向量或自报关联分数。

## v0.4 主动陪伴与独立反思

默认仍是 `cue_only`，不会因为用户说一句“累了”就开放冷库。用户明确开启主动模式后，宿主还要提供本次互动有效的 `memory_mode`、`proactive_scope` 和来源/访问元数据。模型只能使用范围内已选好的记录，不能凭自己的联想扩大搜索。详见[主动记忆设计](../docs/proactive-memory.md)与[示例配置](../config/proactive.example.json)。

主动检索、事实判断、是否说出口分开处理。真实经历、用户自述、助手承诺、反思、猜想保留各自类型；想法不会因为被重复说过就变成事实。主对话在一次正常回复里决定 `use / ask / silent`，不为每个候选再调用模型。保留 hot 内的状态320 / 近期细节320 / 话题事实320；最终召回最多2条事件和可选1条反思，反思最多96 token，合计仍限3条、480 token，记忆总块仍为1600。

反思区不在空闲时翻冷库。只有新增、已完成、获准的真实近期事件才能触发维护；无新增就不调用。后台维护整条链每天最多2次尝试，失败与重试也算，间隔至少6小时；每次完整输入最多2000、输出最多300 token，每日合计4000/600。辅助模型、嵌入、分类和重排共用这份额度，不能各领一份。宿主负责计数、预留输出、持久账本、去重与互斥；无法可靠执行时关闭后台模型维护。每次最多提出2项反思变更。以上都是待实测的起始参数，不是已验证的省费比例。

## 维护输入约定

`new_user_events` 只包含新增、已验证身份的用户原消息及 `event_id / interaction_id / owner_id / scope_id / occurred_at`。`candidate_records` 是宿主根据相同事实键或本次线索在权限范围内挑选的少量候选；绝不能把全库用于每轮去重。内部维护可进行受限索引比对，但不能把无关冷记忆带回主对话。

`recent_context` 是有限近期窗口，只用于指代解析，不是新增记忆来源。`allowed_record_ids` 由程序列出可操作 ID，不能从用户文本中直接接受存储路径。抽取输出不修改热度或 tier，计数与升降层由程序根据原事件执行。
