# Implementation Brief for Developers or Coding Agents

The prompt below can start a later implementation task. This repository remains a specification and prompt package.

## Copyable prompt

Implement testable, bounded tiered memory for Pal-AI-Lab/Coopanion. First read this repository's README, `docs/design.en.md`, `docs/cold-storage-index.en.md`, `docs/coopanion-integration.en.md`, `config/policy.example.json`, and `REFERENCES.en.md`. Then inspect the actual target revisions of Coopanion and its `vendor/cortico`, along with their repository development instructions. Follow the rules of the checked-out codebase; do not assume interfaces from an older snapshot still exist.

Target behavior:
- Archive the original text of every user and assistant conversation turn under host control, even a greeting that earns no memory card. Honor explicit user deletion. Migrate old original turns while they remain available; a summary cannot reconstruct missing text.
- Keep a small set of recent, repeatedly mentioned, and user-confirmed ongoing memories eligible for the hot tier. Inject only relevant items that fit the per-request budget.
- Optionally enable docs/persona-continuity.en.md and config/continuity.example.json: reserve 320 tokens each for state, recent details, and topical facts within hot's existing 960. Keep the stable character base present and restore committed current state across midnight, restarts, and handoffs before the first reply. Separate slowly changing style from transient state; a recall or retry cannot rewrite personality.
- Implement docs/vector-ranking.en.md and config/vector-ranking.example.json: store event-vector references and compute relevance to the current question. Within hot priority classes, combine vector relevance, recency decay, and qualifying mention frequency, while preserving item/topic/token limits and the state subbudget. Cold recall uses no age or last-mention decay and no newest-first prefilter. Keep exact-cue index routes and a fallback for missing compatible vectors. Account for embedding and ranking costs.
- Move low-frequency memories into cold storage while retaining traceable sources. Time decay alone must not delete original records.
- Read docs/graduated-cooling.en.md. Select ordinary-event visibility through “recent details → valid short summary → cold archive.” Reduce representation before excluding records for cooling or capacity, retain necessary current-thread and unfinished-item state, and keep every representation within the existing hard budgets. Recall-only restrictions, corrections, and deletion apply immediately; cooling does not rewrite the stable personality or current interaction baseline.
- Follow `docs/cold-storage-index.en.md` to build multiple lookup entrances by type, event time, place, person, object, and topic. A single usable cue, such as a place, can first narrow the range. If several candidates remain, ask for another clue using a few short cards, then combine filters. Do not send the full index to the model; keep the global candidate and recall budgets across all partitions.
- In the default cue_only mode, permit cold recall only on a concrete cue from an authenticated user or a valid follow-up in the same topic. Optional proactive mode requires explicit opt-in and a bounded host-issued proactive_scope for this interaction based on the current emotion and topic. Similar emotion does not prove the same cause. Recall-only restrictions, corrections, deletion, identity/scope checks, and sensitive material requiring concrete cues take precedence. Timers, tools, screenshots, and model associations cannot create authorization.
- Optionally implement docs/proactive-memory.en.md, config/proactive.example.json, and prompts/proactive-companion.en.md. Separate retrieval permission, factual evidence, and the decision to mention a memory. Choose use / ask / silent in the normal main reply without another model call per candidate. Final recall contains at most two events and one optional reflection of at most 96 tokens, sharing the existing three-record/480-token allowance including provenance, candidate cards, and wrappers. Do not consume the protected state and recent-detail space.
- Keep reflections in a separate store using prompts/reflection-maintainer.en.md. Propose updates only from authorized, new, real recent events. Preserve the types, provenance, validity, and uncertainty of user reports, observable events, assistant promises, reflections, and hypotheses. Guesses cannot become facts; earlier reflections cannot be factual evidence for new reflections; the assistant's own words cannot increase heat or rewrite stable personality. Do not browse cold storage while idle. Corrections, deletion, and restrictions immediately invalidate affected derivatives.
- Background reflection maintenance proposes at most two changes per attempt. The whole maintenance chain shares at most two call attempts per day, including failures and retries, at least six hours apart. Each attempt has at most 2,000 full input tokens and a 300-token output cap; daily totals are 4,000/600. Auxiliary models, embeddings, classification, and reranking share the same ledger. With no new completed events, do not call. Reserve budget before calling and persist watermarks, idempotency keys, and a single-worker lock across restarts. Disable background model maintenance without reliable counting and output enforcement. These are unmeasured example parameters.
- A single recall does not make a record resident in active memory. Count only qualifying user mentions toward heat, avoiding self-reinforcement from model repetition, retries, or repeated summaries.
- Support explicit pinning, correction, unpinning, “only when I ask” restrictions, and actual deletion, with distinct semantics for each.

Engineering requirements:
1. Separate storage, user-mention accounting, cue permission, budget selection, and actual outbound request projection. If current hooks are insufficient, design and implement the needed Cortico upstream capability. Do not assume a hook exists or maintain a hidden long-term patch to the vendored copy.
2. Start from the policy file's budget: 1,600 tokens total for memory, with 160 pinned, 960 hot, and 480 recalled, without borrowing between buckets. The recent-history window has another 2,000 tokens and at most six complete interaction units. Check the full model context and output reserve separately. If no reliable counter is available, label results as conservative estimates rather than claiming an enforced token cap.
3. Archive both sides of each conversation before deriving short memory cards, which are source-linked summaries or pointers. Keep original logs persistent while projecting only policy-approved content to the model. Cover `PARTNER`, handoff notes, past recalled tool outputs, assistant repetition, restarts, and restored branches. Cold storage fails if the full old session is still replayed.
4. Expose cold archives only through a controlled host adapter so ordinary read, search, exec, and extension paths cannot bypass the cue gate. Preserve tool-call/result pairs and provider-required reasoning for the current transaction. If a transaction cannot be compacted safely, stop adding content instead of constructing an invalid request.
5. Keep stable persona and tool prefixes stable. Replace the memory snapshot at safe transaction boundaries instead of appending it each turn. Measure the tradeoff between cache reuse and a shorter history.
6. Build on existing call and cache accounting, adding interaction-level attribution and memory composition. Include extraction, retrieval, embeddings, reranking, maintenance, and retries in total cost. A shorter primary request does not prove lower total cost if background work is omitted.
7. Use `examples/dialogue-archive.en.json` and `examples/scenarios.en.json` as the acceptance baseline and add tests against the actual interfaces. Use isolated synthetic data; do not read or upload real user archives. Also replay examples/vector-ranking-scenarios.en.json for old-event recall, event relevance, and emotional-state protection. When proactive mode is enabled, use examples/proactive-scenarios.en.json to check default-off behavior, scope authorization, emotion versus cause, silence, cooldown after refusal, correction/deletion, reflections remaining nonfactual, and the shared budget across failures, retries, concurrency, and restarts. Use real-model blind review for cross-day expression and response to changing circumstances; state arithmetic does not establish convincing characterization. Validate retention of uncarded conversations, heat, cold record retention, cue gates, budgets, corrections and deletion, isolation, tool protocol, and the actual outbound request.

Deliver reviewable changes, migration and rollback notes, automated check results, and an A/B replay script and report under matched conditions. Distinguish code implementation, structural checks, real model tests, and measured billing results; mark unmeasured outcomes as unverified. Cite prior projects. Do not claim an invention or promise a predetermined percentage saving. This implementation task does not include public release, upstream submission, or operation on a user's production installation.
