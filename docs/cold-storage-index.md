# 远古记忆的逻辑分区与逐步唤回

冷档案保存**所有用户与助手的对话原文**（用户明确删除的内容除外），再按**类型、时间、地点、人物、物品、话题**建立可组合的索引。用户给出其中任何一个有区分度的线索，就先从该入口定位；再按后续对话补充条件，逐步找到具体事件。无需用户一次说全所有条件。

本文件是待实现规格。逻辑分区可以用数据库索引与元数据过滤实现，不要求把硬盘真的分区，也不要求立即引入向量数据库。

## 1. 一条正文，多种入口

例如一段虚构对话：“2019年10月，用户在西安旅行时买了一台胶片相机”。用户与助手的原消息只存一份；从中生成的事件卡和多个索引都指向这段原文的消息 ID。没有被提炼成事件卡的普通聊天也照样归档。

| 入口 | 索引示例 | 可以响应的用户线索 |
| --- | --- | --- |
| 类型 | experience / purchase | 买东西那次、那次旅行 |
| 时间 | 2019 / 2019-10，精度为 month | 2019年、那年十月 |
| 地点 | 中国 / 陕西 / 西安 | 西安、陕西 |
| 人物 | 原文明确提到的人物 ID 或别名 | 跟某个人一起那次 |
| 物品 | camera / film_camera | 相机、胶片相机 |
| 话题 | travel / photography | 旅行时、摄影那件事 |

这些维度没有固定先后顺序。“西安那次”从地点进，“我那台旧相机”从物品进，“2019年那次旅行”从时间与话题进。实现可选择当前最能缩小候选范围的索引，而非强迫所有查询从类型一路下钻。

避免每个类别复制一份完整原文，也不把所有标签、目录树或索引内容发送给主对话模型。索引常驻在宿主的存储中；模型只得到这次被选中的少量候选卡或正文片段。未生成事件卡的旧对话仍可在获准后按原文索引检索，不能因为标签不全就把整库交给模型扫描。

## 2. 字段约定

每个记忆记录增加 `facets`，示例见[记忆数据](../examples/memories.json)。字段由原文证据支持；可选抽取器提出候选，宿主核验后写索引。

| 字段 | 规则 |
| --- | --- |
| types | 一条记录可有多个有限类型，如 experience、purchase、preference、project、relationship、routine、fact |
| occurred_time | 事件实际发生时间；start/end 为含边界的 ISO 日期，precision 为 day/month/year/unknown；未知用 null，不从入库时间猜 |
| places | 规范地点 ID、可读名称、层级与别名；只依据明确资料，未知或“附近”保留模糊性 |
| people | 角色/人物实体 ID 与原文名称；同名不直接合并 |
| objects | 物品类别或实体 ID，例如 camera；不能从“相机”补造品牌和型号 |
| topics | 少量主题标签；规范词与用户原说法可建立别名映射 |

每个维度最多 4 个标签/实体，别名列表单独由宿主维护；不要把所有名词都变成无限标签。`created_at` 是入库时间，`last_user_mention_at` 是热度时间，均不等于 `occurred_time`。用户问“2019年的事”用发生时间查，不按上次提起这件事的日期查。

相对时间“去年”以当前用户事件的时间和时区转换为区间。“当年”“很久以前”没有唯一年份，保留为模糊线索，不编造年份过滤器。未知事件时间的记录应放在显式的 unknown 桶；如果用户仅给地点，可以正常命中它。若用户给精确年份，未知时间不能当作确定匹配，可在未命中后询问是否放宽时间范围。

owner_id、scope_id 与 status 是权限/有效性过滤，不能为了找不到结果而放宽。其他维度是查询条件，只有用户的新线索或明确同意才能改变已明确的条件。

## 3. “你还记得当年在西安那次吗”如何处理

以下全为虚构案例与预期行为：

```text
用户：你还记得当年在西安那次吗？
  用户线索：地点=西安；时间=模糊；类型/物品/话题=暂未指定。
  宿主：先筛同一用户/会话范围内的有效记录，再用“西安”地点索引找候选。
  不做：强行猜2019年、要求用户先给年份、读出全部西安正文。

如果只有一条高匹配记录：返回其必要摘要，保持不确定处。
如果有多条：最多返回3张极短候选卡，合计仍不超过480tokens。
  卡片1：2019年，西安，旅行中购买胶片相机。
  卡片2：2021年，西安，和朋友参加摄影展。

助手：你说的是买相机那次，还是看摄影展那次？
用户：买相机那次。
  宿主：继承未过期的地点线索，加物品=相机、类型=购买，再查一次。
  本次新线索：一次新的查询机会；总候选上限仍为12，不按分区相乘。
  最终：返回匹配的相机事件短摘要与来源；不补造相机型号。

用户换话题后：候选卡与正文都从后续请求投影中退出，原始档案继续冷存。
```

“明确线索”是足以限定有意义范围的线索，并不要求明确到唯一事件。地点线索可以先触发索引筛选；只有完全无定位信息的“你还记得那次吗”才先问线索。若候选很多，不能把最晚3条伪装为完整结果；宿主标记 `truncated=true`，助手简短询问年份、人物、物品或事件类型，不逐页输出全部目录。

候选卡只包含记忆 ID、短标题、已知时间和区分所需类型/物品，属于召回预算的一部分。只展示匹配用户线索且通过权限过滤的候选；没有检索结果时不编造选项。对精确查询出现多个冲突答案，应表达不确定并补充询问。

## 4. 检索流程与硬边界

1. **确认用户来源与许可。** 当前用户线索或有效同话题续问；后台事件不能进入流程。
2. **解析已有线索。** 宿主先用规则与实体别名映射；必要时可用有限输入的线索判定器。模糊词留空，不产生虚假精确条件。
3. **索引过滤。** 先 owner/scope/status，再组合已有的时间、地点、类型、人物、物品、话题。同一维度允许经核验的同义词 OR，不同明确维度通常取 AND。
4. **有限候选排序。** 采用数据库/倒排索引；需要语义搜索时，只在已授权范围内使用且在返回正文前复查过滤。传给正文选取阶段的候选全局最多12条，不能每个分区各取12条再无界拼接。大范围命中允许宿主看总数或截断标记，但不把完整列表交给模型。
   启用[向量排序扩展](vector-ranking.md)时，授权范围内的语义与精确索引路径可各取最多12个宿主内部引用，合计最多24个，先融合、去重并保护有强精确证据的优先组，再将全局最多12条候选交给正文选择阶段；内部引用不代表读取24段正文或发给模型。若优先组仍超限，标记截断并补线索。冷库按当前线索匹配，不使用事件年代或最近提及的衰减，也不能先取最新12条再检索；明确年代按事件发生时间匹配。向量缺失时仍可用精确索引，不能因此放宽已明确的条件。
5. **判别是否唯一。** 范围足够明确则取必要正文；仍有歧义时取最多3张极短候选卡，引导用户提供下一线索。候选卡与正文共用3条/480tokens，不能各占一份预算。同一ID的卡片升级正文是替换，不追加。
6. **压缩后注入。** 使用有来源的原子摘要，连同时间和ID计量；超限优先减少条目。需要长材料时必须是用户明确要求的独立任务，不能自动把整段远古对话作为普通记忆注入。
7. **退出。** 许可到期、话题改变、删除或更正后移除临时内容；有效提及与热度仍按主设计执行，检索读次数不加热。

同一明确线索默认只执行一次检索流程。流程中可以进行有限的索引查找与排序，但不自动尝试无限多组放宽条件；用户新补充线索后才启动下一次。未命中不跨用户/会话找答案，也不静默删掉用户明确给出的地点或时间限制。

对于“详细回顾我在西安的所有旅行”这类明确的大范围请求，可建立单独、可见的分页任务。每页仍有上限，并告知覆盖范围与未读部分，不能把一次广泛授权当作往后所有对话都能自动翻档案。

## 5. 节省 token 的位置

数据库索引过滤本身无需将正文发给语言模型。节省来自“先筛范围、后读少量、最后只注入必要摘要”；如果改成每次把全目录交给模型选分区，或每个分区都调用一个模型，可能反而增加 token 与延迟。

关键词查询或本地索引不直接产生主模型输入 token，但数据库仍有计算/存储成本；云端嵌入、重排、分类和维护若调用模型，全部计入评估。此结构约束了读取范围，不代表已经证明某个费用下降比例。

## 6. 验收补充

- 只有地点线索也能进入正确索引；“当年”不会被擅自转换成年份。
- 时间、地点、人物、物品、类型、话题均可单独作为入口；缺失维度不阻断其他入口。
- 补充线索后组合筛选，最终请求中不出现其他分区的无关正文或完整索引。
- 同一记录多入口仍只有一个 memory_id、一个来源集、一个热度计数，不重复占预算。
- 正确处理别名、同名、时间不详和地点不详；未命中时不猜。
