# 细节怎样自然冷却

目标是让近期常聊的事保持具体，少提之后先留下能接话的短摘要，再从当前上下文撤下。原话始终在冷库里，用户给线索时仍能找回来。这里描述待实现的存储与上下文优化规则，不是已实现的自然遗忘或已验证效果。

## 1. 三个表示阶段，原文只存一份

| 阶段 | 当前可用内容 | 仍然保存什么 |
| --- | --- | --- |
| detail：保留细节 | 有辨识度的原句片段、具体人物/时间、没说完的话、约定条件 | 完整双向原话及来源 |
| summary：精简摘要 | 事件要点、关键限定、下一步和来源；不只写“聊得很开心” | 原文和可追溯的派生表示 |
| cold：退出上下文 | 默认不发送；用户给线索时做有限召回 | 原文、逻辑索引及合法的派生记录 |

`representation_stage` 不新增存储分区。detail 与 summary 都是同一记录的受限派生视图；原始对话只归档一份，同一 ID 每轮只发一种表示，不重复计数或叠加两个版本。普通阶段的 detail/summary 对应 hot 候选；cold 不在 hot 中。候选不保证每次注入，仍要与当前对话相关。

稳定性格底座、当前已提交的 `continuity_state`、用户固定的 pinned 不采用普通事件冷却计时；继续遵守各自的更新、限制调用、删除和预算规则。性格历史版本和久远事件可以冷藏，当前性格与相处基线保持精简可用，详见[连续性设计](persona-continuity.md)。

## 2. 确定性的阶段选择

示例初值由[基础配置](../config/policy.example.json)的 `lifecycle.representation_policy` 定义，未经真实用户实验。只按最近一次经过验证的用户有效提及计算连续时长；陈述时间与事件发生时间分开，不按午夜、重启或摘要写入时间重新计时。

普通事件的选择顺序：

1. **先处理有效性与用户控制。** deleted 不可再用；superseded 不作当前事实；“问到再说”立即转为仅可按用户线索召回。更正、删除和权限限制不等待渐进阶段。
2. **使用已有类型例外。** 当前连续性状态与 pinned 走各自规则。正在执行的工具事务保持协议完整，在安全边界替换快照。
3. **尚未满足 cold 条件时，前72小时优先 detail，之后优先 summary。** 若最近真实用户又实质提及一个仍为 hot 的条目，更新来源后可重新进入细节优先期。助手复述、检索、维护摘要和重试均不刷新计时。
4. **普通时间冷存须经过摘要适用期。** 没有有效进行中标记的普通条目，从最近有效用户提及起满7天且 heat 低于0.30，或满14天无有效提及，才满足普通 cold 条件；其间至少有24小时处于摘要适用期。有效进行中事项先保留预算内、当前相关的紧凑状态，并受复核期限约束，不因上述低热度或失活条件直接冷藏。
5. **已是 cold 的条目不靠后台读写自行升温。** 继续使用原有用户线索召回和重新升温条件。一次召回只服务当前许可话题，不自动恢复完整细节常驻。

可写成以下宿主选择逻辑；它不是现有 Coopanion API：

```text
先过滤删除、失效、权限与 recall_only
按类型处理 current continuity_state / pinned 的专用规则
普通记录若原本 cold：保持 cold，除非已有合法召回或升温依据
否则 age = 当前时刻 - 最近有效用户提及时刻
若有有效 ongoing：按 age 选 detail 或 summary，期限到后 needs_review
否则若 摘要适用时间 >= 24小时，且满足以下任一条件：
    (age >= 7天 且 heat < 0.30) 或 age >= 14天，则目标为 cold
否则：age < 72小时目标为 detail；其余目标为 summary
再做表示核验、当前相关性、条数与 token 预算选择
```

调整参数时核对时间顺序：正常冷存宽限应不短于细节优先期加摘要适用期；默认7天大于72+24小时。7天候选宽限仍不代表一定注入7天，也不代表每次提及都能强行占一个槽。冷却是宿主对“下一次能看到什么”的选择，不能先发送完整原文，再要求模型自行忽略。

## 3. 摘要先准备，过渡不靠反复总结

处理新增事件时，给同一记录准备有来源的 detail 与较短 summary。两种表示都从允许的原始来源生成并核验，不不断总结旧摘要，以免姓名、否定、约定和时间逐步走样。切换表示不复制完整原文，也不新建一个同义事实 ID。

必须保留：谁说的、重要否定、陈述时间、已知事件时间、身份与区别线索、未完成约定的责任方/条件/复核点，以及来源 ID。必要的短原句可保留，例如“怕坚持不下来”；不能把它改成“已经放弃跑步”。

旧摘要未经核验或关键字段放不下时，记录 `summary_unavailable`。若条目仍有 hot 资格且预算容纳，可以暂用上一个有效细节表示；否则以质量或容量原因排除/冷存，并保留原文。不能造出一个看似平滑、实际丢掉关键限定的摘要。

冷记录恢复细节仍须通过现有用户线索或升温许可。表示切换不能变成绕过冷库门控的自动全文读取。

## 4. 预算紧张时怎样选择

权限、当前相关性和独立预算先过滤。对当前相关且尚未结束的任务/约定，优先保留必要的紧凑承接信息，再按基础热度、最近用户提及时间与 ID 的稳定排序处理其他记录。当前协议必需的工具内容仍计入受限任务预算，不能借“约定”无限扩张。

普通候选按“当前相关的未完事项核心优先 → heat降序 → 最近用户有效提及降序 → ID升序”稳定排序，同组同样使用后三个键。条数或主题数量超限时只能按该顺序选整条，压缩文本不能绕过条数限制。

超限时先尝试把低优先级 detail 换成已核验的 summary；仍超限再移除低优先级整条，记录 `capacity` 等排除原因。活跃候选池64条、请求最多8条、每主题最多2条、各 token 子预算均不改变；启用连续性配置时仍是 hot 内320/320/320，总记忆1600。pinned 超限仍需明确的固定管理，不静默撤销已有固定。

连续性配置的72小时近期候选窗口与表示阶段分开：超过近期窗口的普通事件若仍具 hot 资格且与当前话题有关，可用短摘要竞争“话题事实”子区；不能自动占用该区，也不能把旧事件塞进常驻性格状态。记录转入不同子区时按同一 ID 替换与去重，不同时占两个槽。未完成事项则按有效进行中或复核规则处理。

未完成约定超过近期窗口或复核期时标为 `needs_review`，不能写成已完成。真实提醒交给任务系统；这里保护的是必要的任务状态，不是保证所有原句永远都随请求发送。

## 5. 自然过渡的实际边界

正常情况下会依次经历细节优先、摘要优先、冷存；这能减少一刀切，但不是“永不忘细节”的保证。容量不足、缺少合格摘要、显式删除或限制调用可以打断优先过渡，必须记录原因，不能悄悄超出预算。

维护是下一次交互时惰性计算。若用户15天后才回来，计算可以直接得到 cold；中间的摘要适用期已经按真实时差经过，但不等于用户实际看过一条摘要。不能为了补演过渡而主动加载无关旧事，或虚构离线期间发生的互动。

验收规格见 [cooling-scenarios.json](../examples/cooling-scenarios.json)。这些案例验证目标仍待实现，不能报告为已通过的运行或模型测试。
