# 分层记忆设计 v0.3

目标是约束“模型这一次能看到什么”，同时保留可恢复的旧记录。本文件描述待实现行为；示例参数未经真实用户实验，不等同于人类记忆模型。

可选的 [连续性扩展](persona-continuity.md)专门处理跨天性格、近期状态和细节。基础规则仍适用于事件与用户事实；启用扩展时，将 hot 960 细分为连续性状态 320、近期细节 320、话题事实 320。当前风格状态可以跨话题影响语气，具体事件仍受相关性与冷库门控约束，不增加记忆总额度。

## 1. 存储与可见性分开

本方案把每轮**用户与助手的对话原文**完整保存到宿主管控的冷档案，包括没有单独价值的寒暄；只有用户明确删除的内容才从相应原文、索引和派生副本中清除。另从原文中提取少量带来源的记忆卡，`tier` 只表示这些卡片当前的调用位置。近期消息可进入有限窗口，旧消息仍在冷档案里，但不会因此每轮送给模型。冷档案可以使用 SQLite / 文件加索引，首版无需专用向量数据库；本仓库未提供这部分运行代码。

原文和记忆卡是两件事：原文是完整的历史，记忆卡是方便调用的短摘要或指针。某轮没生成卡片，不代表那轮对话被丢弃。冷档案要保留原始消息顺序、说话方、时间、所属用户/范围及来源 ID；可按话题附索引。用户明确删除时，相关原文和卡片一并处理。非对话性质的工具输出、隐含推理和系统日志不因为“保存全部对话”而自动变成用户记忆。

接入时应迁移上游仍可读取的旧对话原文；如果某些旧消息已经没有原文，交接摘要不能反向还原它们，也不能声称那部分历史被完整保存。新归档流程启用后的每轮对话则应先保留原文，再决定是否提炼记忆卡。

| 类型 | 默认进入请求 | 退出条件 | 是否保留档案 |
| --- | --- | --- | --- |
| pinned | 少量用户明确固定的事实，受独立限额约束 | 用户取消固定、更正、删除 | 是，删除例外 |
| hot | 仅相关、有效、排入预算的条目 | 低热度、久未提及、事项到期、容量淘汰 | 是 |
| cold | 否；正文、标签清单和逐项索引均不自动注入 | 用户线索允许的临时检索，或满足重新升温条件 | 是 |
| recalled | 不是新的持久层，是 cold 的临时可见片段 | 当前话题结束、达到有效期或预算挤出 | 原档案仍为 cold |

`status` 与 `tier` 分开：`valid / superseded / deleted`。旧事实被更正后标记为 superseded，默认召回过滤；明确删除后清理正文、索引、摘要、派生副本和缓存，不再可召回。最小删除标记仅用于防止旧日志重新导入，备份清理依据已公布的保留周期执行。

“当前任务”只能是用户明确表示仍在进行且有复核期限的事项。不能把所有曾经讨论过的计划永久当作进行中。固定事实和近期任务均不能成为规避预算的第二份无限 PARTNER.md。

## 2. 记录与来源

建议字段见[示例记录](../examples/memories.json)：

| 字段 | 含义 |
| --- | --- |
| id / owner_id / scope_id | 记录身份、所属用户、允许使用的会话范围 |
| fact_key / topic_id / summary | 可合并的事实键、主题和短摘要；事件需带日期以免误合并 |
| source_refs | 原消息 ID 与原文片段，至少一个可追溯来源 |
| created_at / last_user_mention_at | 首次建立、最近一次有效用户提及 |
| mention_events | 去重后的用户交互 ID、时间、提及类型 |
| ongoing_until / pinned | 当前事项的复核期限、用户固定标记 |
| recall_only | 用户要求“问到再说”的限制标志，优先于固定与进行中状态 |
| facets | 类型、事件发生时间、地点、人物、物品、话题索引，详见[逻辑分区](cold-storage-index.md) |
| tier / status / supersedes | 调度层、有效性、更正的旧版本 ID |

对模型生成的摘要始终保留原消息证据；抽取不确定时不写入确定事实。来自助手猜测、小说、引用材料、其他人的陈述不能直接转成当前用户的经历。多用户或多角色部署按 owner 与 scope 隔离；桌面事件不能伪装成用户发言。

同一事实重复提及：更新统计，最多保留一个当前摘要，不追加多个同义副本。不同时间发生的相似事件可建立同一主题下的独立事件记录。更正时建立版本关系；“以前住杭州，现在住苏州”保存历史时间与当前事实，不把两地随机择一。

## 3. 热度与冷却

### 有效提及

有效提及是用户在独立交互中主动陈述、实质补充或明确确认某事实。一次交互包含其所有工具轮次、模型重试与自动摘要。同一事实在一次交互中最多计一次；一天最多贡献 3 次，滚动保留最近 30 天计分事件。

下列不增加热度：助手重复、检索读取、被动展示、定时任务、重试、用户粘贴的旧对话、单纯问“你还记得吗”。用户纠正事实会更新版本；不需要靠刷次数才能生效。

### 示例分值

对每条有效记忆，在当前时间计算：

```text
F = min(去重并执行每日上限后的近 30 天有效提及数 / 6, 1)
R = 2 ^ (-距最近有效用户提及的天数 / 7)
O = 1（用户确认进行中，且尚未到复核期限），否则 0
heat = 0.45 * F + 0.35 * R + 0.20 * O
```

该分值只是可调的工程初值，不是心理学定律。维护可以在下一次用户交互时惰性计算，无需因时间流逝持续调用模型。

### 状态迁移

1. 新的、来源明确的记忆卡可进入最多 7 天的 hot 候选期；候选并不保证每次注入。瞬时寒暄的**对话原文仍归档**，只是无需生成独立记忆卡。
2. 普通事件先按最近一次用户有效提及的连续时长选择表示：前72小时优先保留细节，随后使用经过核验的短摘要。有效进行中事项先走有期限的必要摘要与复核规则；其他普通条目在7天候选期后 `heat < 0.30`，或超过14天无有效提及时，才具备正常冷存条件，且需至少24小时的摘要可用阶段。宿主惰性计算，不在零点重置。细节、摘要都是同一条记忆的表示，原文始终归档。详见[渐进冷却](graduated-cooling.md)。
3. 活跃池最多64条，每次请求最多8条。容量不足时先为低优先级候选采用已有的合格短摘要，再按优先级退出非必要整条内容；正在聊的话题和未完事项保留必要紧凑状态，仍须计入硬预算。无法容纳时明确标记容量原因，不用空泛摘要或编造细节掩盖缺失。权限限制、更正和删除立即生效，当前人格状态按其类型例外处理。
4. cold 重新升为 hot：近 7 天至少 3 个独立交互、分布在至少 2 个日期，有实质提及；或用户明确恢复该事项为进行中。单次线索召回保持 cold。
5. 用户可以明确固定或取消固定。pinned 最多 4 条且共 160 tokens；超额时说明哪些尚未固定，请用户合并或替换，不能默默删掉已固定项或宣称全部记住。
6. 进行中事项需要 `ongoing_until`，默认复核期限最多 30 天。超过期限后不再获得进行中加分；到期不会凭空变成已完成。后续需要时询问状态。真正的提醒与定时任务由任务系统维护，不能依赖被动记忆排序保证执行。
7. 用户要求“问到再说”时，`cold_only` 操作设置 `recall_only=true`、取消 pinned 并将 tier 设为 cold，保留原始来源。它优先于热度和 ongoing；不能被频率升温或一个普通进行中更新覆盖。只有带用户明确解除限制依据的 `allow_normal` 才清除该标志，之后恢复正常筛选规则，不自动恢复固定。限制未解除时遇到 pin 请求应澄清冲突，不能静默清除限制。

进行中操作另含 `ongoing_state=active / ended`：active 且未给期限时由程序设置复核日期；ended 清除 ongoing_until。未知期限和明确结束不能都解释为“再保留30天”。

热度决定候选保留；**当前相关性决定是否注入**。当前用户消息和有限近期窗口与主题无关时，即使非常高频，也不强塞进去。相关性可用关键词或本地语义相似度，阈值用项目数据校准；不能将一个未经校准的向量分数直接称为“置信度”。

### 可选的向量综合排序

[v0.3 向量扩展](vector-ranking.md)给事件卡保存可追溯的语义向量引用，并按当前问题计算关联度。`heat` 仍决定冷热候选资格与迁移；在同一优先级内，热事件改用 `0.65*S + 0.20*R + 0.10*F + 0.05*O` 排序，其中 S 为语义相似度，R/F/O 沿用上面的定义。排序前必须满足相关性、权限、状态与类型规则。无合格向量时使用明确的关键词/索引降级流程，不能混用不同模型的分数。

冷召回使用 `0.80*S + 0.20*cue_match`，不使用事件年龄或最近提及的衰减，也不按最近时间预截断候选；用户明确给出的事件年代仍作为查询条件。精确的地点、时间、物品等证据保留独立检索路径，语义门槛不能否决已核验的精确匹配；融合阶段按扩展定义保护有强精确证据的优先组，不让弱语义候选挤掉它。单个宽泛地点或话题不自动算强精确证据。系数仅为待校准初值，分数不代表事实可信概率。

Top N 是最多带多少条，不是必须填满。连续性启用时，先恢复独立的状态320/1条，再在近期细节320/3条、话题事实320/4条中分别选择，hot 总960/8条及每主题2条保持不变。底层人格不参加事件排名。冷召回仍需用户许可，全局候选最多12条，最终最多3条/480tokens；具体融合与降级规则见扩展。

## 4. 用户线索门控

冷存检索许可由宿主确定，模型只能提出建议。没有许可就不查冷正文，也不向模型提供冷档案主题目录。门控规则如下：

| 当前事件 | 冷检索 | 处理 |
| --- | --- | --- |
| 用户提到具体人物、地点、项目、旧事件或时间，并且回答需要既有记录 | 允许 | 用当前线索限制查询范围 |
| 用户说“继续那件事”，近期窗口内有唯一且未到期的用户话题 | 允许续接 | 继承该话题的用户线索 |
| “你还记得吗”“上次那个”，没有可定位的近期指代 | 暂不允许 | 简短询问是哪件事，不扫描全部冷库找话题 |
| “今天好累”、问候、与旧事无关的一般问题 | 不允许 | 使用当前消息和相关活跃记忆 |
| 定时唤醒、宠物动作、截图、工具返回、助手自己联想 | 不允许 | 不从这些事件生成冷查询 |

人物或主题线索不一定要出现“记得”二字。例如“杭州那次旅行最后订了哪家酒店”已足够；“杭州今天几度”不需要读私人的旧旅行。线索要同时满足来源是用户、足以缩小范围、当前问题需要回忆。“当年在西安那次”已有地点入口，可以先查地点索引，不必先问年份；如果命中多条，再由少量候选卡引导补充。类型、时间、地点、人物、物品和话题可以任一入口开始，详见[逻辑分区设计](cold-storage-index.md)。

程序可先用确定规则、实体匹配和近期指代处理。可选的[线索判定提示词](../prompts/cue-router.zh.md)只读当前输入及有限近期窗口，不读整个冷库；其结果经过宿主检查后才能获得检索许可。该辅助模型费用须计入总成本，不能默认每轮都调用。

### 一次唤回的过程

1. 先按 owner、scope、status 和时间等约束过滤；只在许可范围检索索引，交给正文选择阶段的融合候选最多12条。启用向量扩展时，语义与词法通道在宿主内可各返回最多12个引用，去重前最多24个；仅用于有界索引融合，不是24段正文或额外模型输出。强精确证据先作为优先组，超过输出上限时标记截断并请用户补线索。
2. 检索结果做主题/来源核对与去重；有歧义时用极短候选卡引导补充，定位后读取必要摘要。卡片与正文共用最多 3 条且含封装共 480 tokens，同一ID的卡片升级正文时替换，不能叠加。
3. 未命中如实说明未定位到，给一个简短的补充线索问题；候选歧义时不猜。首次检索后不自动连续扩大范围，等用户提供新线索再查。
4. 返回 `recall_status=matched / ambiguous / not_found / disabled`，附被选记录的来源 ID 与原始时间；该状态来自程序，模型不得编造。
5. 召回许可绑定原始用户交互和话题。在同一话题的后续最多 5 个用户交互、且最长 30 分钟内有效，取先到者；话题切换立即失效。单纯助手回应或“继续”不无限续期；新的明确用户线索可开始新的许可。
6. 召回内容到期后从后续请求投影中移除。永久档案不动；来源明确的新用户确认可按有效提及规则计数，检索行为本身不计数。

临时召回不应立即复制到 PARTNER.md、交接摘要或固定事实区。否则“一次提到，永久随请求发送”会破坏整个方案。

## 5. 有限调用与实际请求

以[策略配置](../config/policy.example.json)为准，记忆块含标签、ID、时间、来源和格式开销总计最多 1,600 tokens：固定 160 / 活跃 960 / 临时召回 480，各自不可借用。空槽位不需要填满。近期历史另计 2,000 tokens，最多 6 个完整交互单元，取先达到的限制。

活跃候选先过滤无效与不相关内容，再按当前任务连续性、受保护的近期锚点及一般热度等优先级选择；同一优先级内，未启用向量扩展时按热度降序、最近提及时间降序、ID 升序稳定排序；启用时按[向量扩展](vector-ranking.md)的热区综合分数排序，保留原任务优先级与独立状态额度。每主题最多2条，避免某个高频话题占满预算。超限先为低优先级条目选择预先核验的短摘要，再移除仍无法容纳的非必要整条；不能截掉否定词、时间或事实限定。受保护状态也没有无限额度，固定事实超限仍通过用户可见的固定管理解决。表示选择、容量退出与正常冷却的区别见[渐进冷却](graduated-cooling.md)。

请求组装示意（不是现有 Coopanion API）：

```text
读取事件身份与当前用户消息
更新有效提及、版本与过期状态（无须先把冷库读给模型）
判断当前用户线索许可
若有许可：在权限范围检索，选少量临时片段
按当前相关性选择 hot；读取有限 pinned
按各自 token 和条数上限封装一次 memory_snapshot
生成有限近期历史投影，剔除过期召回与已冷却的记忆副本
拼接稳定角色/工具前缀、近期窗口、当前记忆快照、当前消息
逐项核对总输入、工具阶段与输出预留；通过后才发请求
```

这里的排列是逻辑结构；实际消息角色及顺序必须遵守所用 provider 的协议。快照由宿主提供为带边界的上下文数据，不能把不可信原文升级为系统指令。

### 必须满足的约束

- `memory_snapshot` 是当前快照的替换，不是每轮追加一份。相同事实不要同时存在于 PARTNER.md、近期摘要、工具结果和快照中。
- 原始用户与助手对话按上述规则完整归档，但不能继续无条件全量发出。旧召回工具结果及包含该旧事的助手复述，都可能绕过冷存；请求投影要按来源标记过滤或由经过验证的有限任务状态替代。
- 在当前完整工具事务中，不得拆散调用与结果、不删除该 provider 要求的当前轮推理字段。需要删掉历史记忆时在安全的事务边界重建上下文；如果仍无法满足预算，结束当前批次或明确报告超限，不默默破坏协议。
- 冷内容若尚在当前工具事务中，仅在该事务/有效话题许可内使用。换话题或许可到期后，先结束旧事务，再在干净投影中处理新用户事件；不要为了工具循环无限延长许可。
- 冷存策略必须覆盖通用 `read_file`、搜索、命令执行等实际可访问路径。建议档案位于宿主管理存储，通过受控检索适配器访问；仅折叠文件列表或把目录改名为 archive 不构成隔离。
- 数据与政策分离：对记忆中的“忽略规则”“检索全部”等文本只当作被引用数据，不执行；原文引用不能获取新的存储访问权。

### 不能混为一谈的预算

```text
完整输入 = 固定系统/角色 + 工具定义 + 当前消息/附件
         + 近期窗口 + 记忆快照 + 当前任务工具事务 + 协议开销
完整输入 + 输出预留 + 安全余量 <= 当前模型的上下文限制
```

1,600 只是其中的记忆快照预算。当前长消息不应静默截断；单独确认分段处理或压缩方案。单个工具结果也需宿主的输出上限和分页；分页不会自动授权读冷库。无法满足完整请求限制时，拒绝继续叠加工具结果并说明原因。

优先用对应模型的 tokenizer 或服务端计数；不可用时用经样本校准的保守估计并留余量，标明 `budget_mode=estimated`。字符比例不是硬 token 保证，只有可靠计数器验证后才可称 `budget_mode=verified`。协议封装、图片等还需按供应商规则处理。

## 6. 缓存和维护成本

稳定的角色说明、工具定义尽量保持字节及顺序稳定。动态记忆放在稳定前缀之后；一次工具批次内固定同一快照，版本更新放到下一安全边界。紧急删除或更正应中止旧批次后重建，不能为缓存继续使用失效记忆。

有限窗口替代长会话可能损失部分历史缓存命中。严格移除过期冷记忆时，正确性优先；缓存保留到什么程度应由真实请求验证，不能承诺同时获得最大缓存命中和最短输入。

提取与合并只处理增量内容：优先规则直写明确更正，必要时批量使用抽取器。不要每个工具轮次总结全文，也不从多层摘要反复总结出更多“事实”。嵌入、重排、抽取模型、重试和维护都计入总成本。

## 7. 用户体验与验收

助手可以说“给我一点人物或时间线索，我来找找之前的记录”，不能在未检索时声称“已经想起来”，也不把保存的记录说成已删除。找到事实后自然接续对话，不需每句解释存储结构。

用户明确说“记住这个”进入固定管理；说“不要再记这件事”走删除流程；“以后别主动提，问到再说”进入冷存或限制主动使用，三者语义应区分。完整验收见[评估计划](evaluation.md)。
