# 陪伴 AI 记忆上下文 token优化

**English: [Companion AI Memory Context and Token Optimization](README.en.md)**

本方案借鉴人类记忆中“近期常用、久远冷却、线索唤回”的现象，针对 AI 长对话反复加载大量上下文所造成的响应变慢与 Token 消耗增加。以 [Coopanion](https://github.com/Pal-AI-Lab/Coopanion) 为接入目标：**常用的少量留在眼前，低频的进入冷存，久远的按分类索引由用户线索唤回。**

本仓库提供设计、提示词、示例配置与验收用例，供开发者实现和验证。当前版本为 **v0.1 方案与提示词包**，尚未接入 Coopanion，不能作为扩展直接安装，也没有实测 token 节省率。参考 MemGPT、MemoryBank、MemoryOS，不主张分层记忆或遗忘机制的首创性。

## 想解决什么

AI 陪伴需要保持连续性，但不必每次对话都携带所有往事。这里借用电脑“运存与硬盘”的思路：存储容量可以增长，每次交给模型的内容必须有限。

“遗忘”表示旧事暂时退出当前上下文；原始记录仍可检索。它不要求助手假装自己具有人的记忆，也不通过随机删除往事制造拟人效果。

| 记忆位置 | 放什么 | 何时使用 |
| --- | --- | --- |
| 近期对话窗口 | 最近对话及当前任务必需状态 | 保持当前话题连贯，窗口有上限 |
| 活跃记忆（类似运存） | 用户固定的少量事实、反复提到的主题、仍在进行的事项 | 相关时按优先级选取，条数与 token 双重限额 |
| 冷记忆（类似硬盘） | 低频、久远、已结束事项的详细记录 | 当前用户提供人物、事件、时间或话题等线索后才允许检索 |
| 临时召回片段 | 本次线索找到的少量冷记忆 | 仅服务当前话题，结束或到期后退出上下文 |

## 三条核心规则

1. **低频冷存。** 随时间衰减，少被用户提及的记忆退出活跃区，正文与来源保留在冷档案。只把目录折叠起来不够，还要从实际模型请求中移除旧正文与旧召回片段。
2. **用户线索唤回。** “去年杭州那家咖啡店”可以启动检索；普通问候、定时唤醒、工具输出或模型自己想起某件事不能启动冷检索。线索模糊时，请用户补充一句。
3. **高频调用有限。** 只统计用户的有效提及，同一轮重试、助手复述、自动摘要不增加热度；即便高频，也只注入与当前对话有关的少量条目。

## 远古记忆按线索分区检索

冷档案按**类型、时间、地点、人物、物品、话题**建立逻辑索引，同一条记录只存一份，各个分类都是检索入口。

例如用户说“你还记得当年在西安那次吗”，先用“西安”筛选索引；“当年”不代表已知年份。如果找到几件往事，返回少量候选，问“买相机那次，还是看摄影展那次？”用户补充“买相机”，再组合地点、物品和事件类型找到正文。

完整目录与全部西安往事都不进入上下文。候选卡和最终摘要共用召回额度，最多 3 条 / 480 tokens。详见[逻辑分区设计](docs/cold-storage-index.md)和[结构化查询示例](examples/recall-plan.json)。

## 初始预算建议

以下是待实验的初始值，不是 Coopanion 现有配置，也不是最佳参数。

| 项目 | 上限 |
| --- | ---: |
| 每个请求中的记忆总块 | 1,600 tokens |
| 其中：用户固定的事实 | 160 tokens / 4 条 |
| 其中：相关活跃记忆 | 960 tokens / 8 条，每主题最多 2 条 |
| 其中：当前线索召回 | 480 tokens / 3 条 |
| 近期历史窗口（另计） | 2,000 tokens / 最多 6 个完整交互单元 |

各子预算不可互借，没用完就留空。固定事实、当前任务也不能无限增长；详见[预算与例外处理](docs/design.md)。系统提示词、工具定义、当前用户消息、工具执行、模型输出仍要另外计入完整请求与账单。中文字符数不能直接当作 token 数。

## 节省比例：估算与实测

**截至 2026-10-25，没有在 Coopanion 中完成本方案的运行和计费实测，因此没有可填写的“实测节省可达 X%”。** README 与仓库描述不使用这一措辞或百分比承诺。上下文变短也不必然使响应时间、总费用按同一比例下降。

只用于说明计算方法的假设例子：原方案单次请求含固定提示词与工具定义 8,000、重复历史 20,000、当前消息 2,000，共 **30,000 输入 tokens**。若接入后固定部分仍为 8,000、近期窗口 2,000、记忆快照 1,600、当前消息 2,000，共 **13,600 输入 tokens**。按此假设，输入量减少 `(30,000−13,600)/30,000 ≈ 54.7%`，可口语化说“**约 55% 的示例输入缩减**”。这不是 Coopanion 的实测，也不是费用或延迟下降幅度。

真实结果须把所有模型轮次、缓存命中与折扣、输出、工具结果、检索和维护成本合并评估，并同“仅缩短近期历史”的方案对照。具体记录字段和 A/B 方法见[评估计划](docs/evaluation.md)。实测指标应同时报告每次用户交互的总输入 tokens、总费用、响应延迟与记忆正确率；在测量之前，上架文案写“**预期减少重复上下文，节省幅度待实测**”。

## 使用方式

1. 阅读[设计说明](docs/design.md)，确认记忆状态、热度、检索门控和预算规则。
2. 按[Coopanion 接入说明](docs/coopanion-integration.md)实现宿主侧存储、选取、冷检索权限与实际请求投影。需要改变 Cortico 的请求构造行为时，在其支持的扩展点或上游实现。
3. 将[对话记忆策略](prompts/companion-policy.zh.md)作为现有角色提示词的补充；上游接入可参考[英文版](prompts/companion-policy.en.md)。不要用它替换完整人格或工具协议。
4. 用[记忆提取提示词](prompts/memory-extractor.zh.md)生成候选变更，由程序核验来源后写入；[线索判定提示词](prompts/cue-router.zh.md)仅在规则无法判断时选用。
5. 以[示例配置](config/policy.example.json)、[合成案例](examples/scenarios.json)和[评估计划](docs/evaluation.md)验证效果。

**单独粘贴提示词无法保证节省 token。** 当完整历史已经发给模型后，再要求它“只记重要的”并不会减少输入。真正的限制必须在请求发出前执行。

## 对话效果示例

以下为预期行为示例，不是模型实测结果。假设杭州咖啡店记录已经冷存。

> 用户：今天有点累。  
> 助手：今天主要是哪件事让你累？  
> 行为：不主动搜索或提起过去的旅行。

> 用户：去年在杭州，下雨那天我们聊到的咖啡店，你还记得吗？  
> 行为：用户线索允许检索，只返回与杭州、下雨、咖啡店匹配的少量记录。  
> 助手：找到了之前的记录，你说的是河岸咖啡。那天你提过想找个能安静看书的位置。

> 用户：不是那家，是靠近车站的。  
> 行为：使用新线索修正检索；找不到就说明未定位到，不编造店名。单次召回不会自动让整段旅行成为常驻记忆。
